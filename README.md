# Описание кода: барьер для потоков (`Barrier`)

## Что такое `Barrier`

`Barrier` — это примитив синхронизации из `std::sync`, который **заставляет несколько потоков ждать друг друга в одной точке** программы. Поток, дошедший до `wait()`, блокируется и не продолжает выполнение, пока **все** потоки не вызовут `wait()`. Как только последний поток доходит до барьера, **все потоки одновременно освобождаются** и продолжают работу.

Это похоже на «сбор всей команды перед стартом»: никто не бежит, пока все не собрались.

## Разбор кода по частям

### 1. Создание барьера

```rust
let b = Arc::new(Barrier::new(3));
```

- `Barrier::new(3)` — создаёт барьер, рассчитанный на **3 потока**.
- `Arc` (Atomic Reference Counted) — умный указатель с атомарным подсчётом ссылок, позволяющий **безопасно разделять владение** между потоками.
- `Arc::new(...)` оборачивает барьер, чтобы его можно было клонировать и передавать в потоки.

Число `3` — это **количество участников**. Если хотя бы один поток не дойдёт до `wait()`, остальные будут ждать вечно (deadlock). Это критично: число должно точно совпадать с реальным количеством потоков, которые вызовут `wait()`.

### 2. Создание вектора для хранения хендлов

```rust
let mut h = vec![];
```

- `h` — вектор, в который будут складываться `JoinHandle` от каждого потока.
- `JoinHandle` позволяет потом дождаться завершения потока через `.join()`.
- `mut` нужен, потому что мы будем добавлять элементы через `push`.

### 3. Запуск трёх потоков

```rust
for i in 0..3 {
    let b = b.clone();
    h.push(
        thread::spawn(move || {
            println!("Thread: {i}, before wait.");
            b.wait();
            println!("Thread: {i}, after wait");
        })
    );
}
```

Разберём по строкам:

- **`for i in 0..3`** — цикл от 0 до 2 (три итерации).
- **`let b = b.clone()`** — клонирует `Arc<Barrier>`, увеличивая счётчик ссылок. Каждый поток получает **свою копию** `Arc`, но все они указывают на **один и тот же** `Barrier` внутри.
- **`thread::spawn(move || { ... })`** — создаёт новый поток:
  - `move` — замыкание **забирает владение** `b` и `i` (копирует их внутрь потока);
  - `i` — целое число, копируется по значению (тип `i32` реализует `Copy`);
  - `b` — `Arc`, клонированный ранее, теперь перемещается в поток.
- **`println!("Thread: {i}, before wait.")`** — печатается **до** барьера.
- **`b.wait()`** — ключевой вызов: поток блокируется, пока все 3 потока не вызовут `wait()`.
- **`println!("Thread: {i}, after wait")`** — печатается **после** барьера, когда все потоки освободились.
- **`h.push(...)`** — сохраняем `JoinHandle` в вектор, чтобы потом дождаться завершения.

### 4. Ожидание завершения всех потоков

```rust
for t in h {
    t.join().unwrap();
}
```

- `for t in h` — перебираем все `JoinHandle` (вектор потребляется, `h` перемещается).
- `t.join()` — **блокирует главный поток**, пока соответствующий поток не завершится.
- `.unwrap()` — если поток паниковал, `join()` вернёт `Err`, и `unwrap()` вызовет панику в главном потоке (это нормально для примера — мы хотим знать о падениях).

## Что гарантирует барьер

### Гарантия 1: Порядок вывода «before»

Все три строки `Thread: N, before wait.` **гарантированно** напечатаются **до** любой строки `Thread: N, after wait`.

Это потому, что `wait()` блокирует поток, и ни один поток не может дойти до `after wait`, пока все три не вызовут `wait()`.

### Гарантия 2: Одновременный старт «after»

После того как последний поток вызовет `wait()`, **все три потока освобождаются одновременно**. Порядок вывода `after wait` между потоками **не гарантирован** — они бегут наперегонки.

## Пример вывода

```
Thread: 0, before wait.
Thread: 1, before wait.
Thread: 2, before wait.
Thread: 2, after wait
Thread: 0, after wait
Thread: 1, after wait
```

Обратите внимание:

- **Строки `before` всегда идут первыми** — это гарантия барьера.
- **Порядок `before` между потоками** может варьироваться (потоки стартуют не мгновенно).
- **Порядок `after`** тоже варьируется — после освобождения потоки бегут параллельно.

Возможен и такой вариант:

```
Thread: 1, before wait.
Thread: 0, before wait.
Thread: 2, before wait.
Thread: 0, after wait
Thread: 1, after wait
Thread: 2, after wait
```

Но **никогда** не будет такого:

```
Thread: 0, before wait.
Thread: 1, before wait.
Thread: 0, after wait      // ❌ невозможно
Thread: 2, before wait.
```

Потому что поток 0 не может выйти из `wait()`, пока поток 2 не вызовет `wait()`.

## Зачем нужен `Arc`

`Barrier` **не реализует `Clone`** — его нельзя просто скопировать. Но `thread::spawn` требует `'static` и `move`, то есть поток должен **владеть** всем, что использует.

`Arc<Barrier>` решает это:

- `Arc` можно **клонировать** (`b.clone()`), и каждый клон указывает на **тот же самый** `Barrier`.
- Когда все потоки завершатся, счётчик ссылок `Arc` дойдёт до нуля, и `Barrier` будет освобождён.

Без `Arc` пришлось бы использовать `'static`-ссылку или другие хаки, но `Arc` — идиоматичный способ.

## Типичные ошибки

### 1. Неверное количество участников

```rust
let b = Barrier::new(3);
// но запускаем только 2 потока
```

Оба потока навсегда зависнут в `wait()`, потому что третий никогда не придёт. Это **deadlock**.

### 2. Забыли клонировать `Arc`

```rust
for i in 0..3 {
    h.push(thread::spawn(move || {
        b.wait();   // ❌ ошибка: b перемещён в первый поток
    }));
}
```

Компилятор не даст это сделать — `b` перемещается в первое замыкание и больше недоступен.

### 3. Вызов `wait()` из главного потока

Если главный поток **тоже** вызовет `wait()`, а барьер рассчитан на 3 потока (из которых 3 — рабочие), то главный станет **четвёртым участником**, и барьер никогда не сработает.

## Когда использовать `Barrier`

| Сценарий | Подходит? |
|---|---|
| Разделить фазы вычислений: все потоки должны закончить фазу 1, прежде чем начать фазу 2 | ✅ Да |
| Синхронизировать старт нескольких потоков (все ждут сигнала) | ✅ Да |
| Заменить `Mutex` для защиты данных | ❌ Нет |
| Дождаться завершения всех потоков | ❌ Нет, для этого `join()` |
| Ограничить доступ к ресурсу | ❌ Нет, для этого семафор или `Mutex` |

## Сравнение с другими примитивами

| Примитив | Назначение |
|---|---|
| `Barrier` | Все потоки ждут друг друга в одной точке |
| `Mutex` | Взаимное исключение: только один поток владеет ресурсом |
| `RwLock` | Много читателей ИЛИ один писатель |
| `Condvar` | Ожидание выполнения условия |
| `mpsc::channel` | Передача данных между потоками |
| `JoinHandle::join` | Дождаться завершения конкретного потока |

## Итог

- `Barrier::new(N)` создаёт барьер на **N потоков**.
- `Arc<Barrier>` позволяет разделять барьер между потоками.
- `b.clone()` даёт каждому потоку свою ссылку на **тот же** барьер.
- `b.wait()` блокирует поток, пока все N потоков не вызовут `wait()`.
- После этого **все потоки освобождаются одновременно**.
- Гарантия: все «before» напечатаются до любого «after».
- Число участников должно **точно** совпадать с количеством вызывающих `wait()` — иначе deadlock.
- `join()` в конце нужен, чтобы главный поток дождался завершения всех рабочих потоков.
